# خطة إعادة تصميم التطبيق

## أهداف المشروع

- إعادة تصميم تطبيق مِلاك ليصبح مناسباً لمجال إدارة الإيجارات والعقارات، وليس مجرد واجهة عامة.
- الحفاظ على جميع وظائف التطبيق الحالية بدون تغيير السلوك أو قاعدة البيانات إلا بعد موافقة منفصلة.
- توحيد الهوية البصرية، الألوان، الخطوط، المسافات، الأزرار، البطاقات، الحالات، والنماذج.
- تحسين قابلية الاستخدام على الشاشات الصغيرة ومنع القص والـ overflow.
- جعل التدفقات الأساسية أسرع:
  - إضافة عقار.
  - إضافة مستأجر.
  - إنشاء عقد.
  - تسجيل سند قبض.
  - إضافة فاتورة خدمة.
  - فتح بلاغ صيانة.
  - تصدير PDF.
- جعل التطبيق يبدو كأداة عقارية مالية موثوقة: هادئ، واضح، سريع، عربي RTL، ومناسب للاستخدام اليومي.

## استراتيجية إعادة التصميم

الاستراتيجية المقترحة تعتمد على إعادة بناء الواجهة تدريجياً حول Design System موحد، وليس تعديل كل شاشة بشكل عشوائي.

الاتجاه البصري:

- نمط رئيسي: Minimalism + Flat Design + Trust & Authority.
- لمسات مساعدة: Soft UI خفيف للبطاقات والحالات.
- تجنب: Glassmorphism ثقيل، زخرفة زائدة، 3D، gradients مبالغ فيها.
- كثافة: متوسطة/عملية؛ التطبيق إداري ويحتاج عرض بيانات كثيرة بوضوح.
- حركة: خفيفة وسريعة 150-300ms.

الألوان المقترحة:

- Navy أساسي للإجراءات والهوية.
- Teal للعقارات والإشغال.
- Green للتحصيل والمدفوع.
- Red للمتأخرات والأخطاء.
- Orange للصيانة والتنبيهات.
- Gold للعقود والتمييز.
- خلفية فاتحة باردة وسطح أبيض.

قواعد التنفيذ:

- قبل تعديل أي شاشة، يتم تثبيت عناصر مشتركة:
  - Theme tokens.
  - Text styles.
  - App scaffold.
  - Header pattern.
  - Cards.
  - Status badges.
  - Buttons.
  - Form fields.
  - Empty states.
  - Loading states.
- بعد ذلك يتم تعديل الشاشات حسب الأولوية.
- كل شاشة تعدل وحدها ثم تختبر قبل الانتقال للتي بعدها.
- لا يتم حذف أي وظيفة موجودة.
- أي تغيير في التدفق أو قاعدة البيانات يحتاج موافقة منفصلة.

## مراحل التنفيذ

### المرحلة 1: تثبيت Design System

- تعريف ألوان semantic داخل Flutter theme:
  - primary, secondary, surface, background, success, warning, danger, info, contract, utility.
- توحيد الخط العربي والإنجليزي.
- تعريف scale للمسافات:
  - 4, 8, 12, 16, 20, 24, 32.
- توحيد radius:
  - 8 للعناصر الصغيرة.
  - 12 للبطاقات.
  - 16 للـ sheets.
  - pill للأزرار/chips عند الحاجة.
- توحيد shadow/border:
  - border خفيف.
  - shadow محدود جداً.
- توحيد motion durations:
  - fast 150ms.
  - normal 220ms.
  - slow 300ms.

### المرحلة 2: بناء المكونات المشتركة

- AppHeader موحد لكل شاشة.
- StatCard موحد للإحصائيات.
- EntityCard للعقار/المستأجر/العقد/السند.
- StatusBadge موحد.
- ActionButton موحد.
- IconButton موحد مع tooltip/semantic label.
- FormSection للنماذج الطويلة.
- FieldLabel + helper/error.
- EmptyState موحد.
- LoadingSkeleton.
- PDFActionButton بحالة loading واضحة.
- MoreActionButton أو MoreMenu بتصميم مناسب وغير مزعج فوق الفوتر.

### المرحلة 3: إعادة تصميم الهيكل العام

- مراجعة Bottom Navigation.
- نقل “المزيد” إلى نمط أنيق:
  - إما تبويب واضح ضمن Bottom Navigation إذا كان عدد التبويبات 5 أو أقل.
  - أو زر Floating صغير مضبوط فوق Safe Area، لا يغطي المحتوى.
  - أو صفحة More كوجهة مستقلة من أيقونة واضحة.
- تثبيت SafeArea وpadding أسفل القوائم.
- منع أي محتوى من النزول خلف الفوتر.
- توحيد transitions بين الشاشات.

### المرحلة 5: إعادة تصميم النماذج والتدفقات

- الخدمات والصيانة تحتاج ربطاً واضحاً بالعقار والوحدة والمستأجر.

## ما الذي سيتم تحسينه في كل شاشة

### لوحة التحكم

- تحويلها إلى لوحة تشغيل حقيقية لا صفحة بطاقات عامة.
- عرض مؤشرات:
  - إجمالي العقارات.
  - الوحدات المؤجرة/الشاغرة.
  - المستأجرون النشطون.
  - المتأخرات.
  - المحصل هذا الشهر.
  - عقود قريبة الانتهاء.
- إضافة قسم “أهم التنبيهات”.
- جعل البطاقات قابلة للنقر بدون شاشة حمراء أو route ناقص.
- ضبط المقاسات على الشاشات الصغيرة.

### المالية

- إعادة تنظيم السندات والاستحقاقات والمصروفات والخدمات.
- استخدام Segmented Control أو Tabs واضحة.
- منع قص الأزرار أسفل الشاشة.
- جعل زر PDF واضحاً بحالة loading ونتيجة فتح/مشاركة.
- عرض السند كبطاقة تحتوي:
  - رقم السند.
  - المستأجر.
  - العقار/الوحدة.
  - المبلغ.
  - الحالة.
  - التاريخ.
  - إجراءات: PDF، مشاركة، تذكير.
- فصل بنود الإيجار والخدمات داخل السند.

### العقارات

- إضافة بطاقة عقار واضحة:
  - اسم العقار.
  - المالك.
  - العنوان.
  - نسبة الإشغال.
  - عدد الوحدات.
  - الخدمات المتوفرة.
  - الدخل المتوقع.
- تفاصيل العقار:
  - ملخص.
  - الوحدات.
  - المستأجرون.
  - العقود.
  - الخدمات.
  - الصيانة.
- إعادة تصميم نموذج إضافة العقار بأقسام.

### المستأجرون

- ملف مستأجر واضح:
  - بيانات أساسية.
  - العقار والوحدة.
  - الرصيد.
  - العقود.
  - السندات.
  - فواتير الخدمات.
  - الرسائل.
- إزالة أي حقول غير مناسبة عند إضافة مستأجر جديد مثل التأمين أو المتراكمات.
- التأمين يظهر في العقد، وليس في إضافة مستأجر.
- توضيح المديونية بلغة مفهومة بدلاً من مصطلح غامض.

### العقود

- تحويل إنشاء العقد إلى flow واضح:
  - اختيار المستأجر.
  - عرض العقار والوحدة تلقائياً من ربط المستأجر.
  - إدخال المدة والقيمة والتأمين.
  - مراجعة.
  - اعتماد.
- منع تكرار اختيار العقار إذا كان المستأجر مربوطاً بالفعل.
- عرض تحذير إذا كان المستأجر غير مربوط بوحدة.
- تحسين PDF العقد.

### الخدمات والعدادات

- تبقى صفحة مستقلة لأنها كيان مالي وتشغيلي مستقل.
- تظهر أيضاً من داخل المستأجر والعقار كملخص.
- تقسيم الخدمة حسب:
  - عداد مالك.
  - عداد مستأجر.
  - عداد مشترك.
  - غير متوفرة.
- عند اختيار مستأجر، يتم تطبيق سياسة العقار/الوحدة تلقائياً.
- فاتورة عداد المستأجر لا تدخل المديونية إلا إذا اختار المستخدم ذلك صراحة.
- سند قبض يستطيع تحصيل الإيجار والخدمات كبنود منفصلة.

### الصيانة

- في نموذج بلاغ الصيانة:
  - اختيار العقار.
  - قائمة الوحدات تتغير حسب العقار.
  - عند اختيار الوحدة يظهر المستأجر إن وجد.
  - إذا لا يوجد مستأجر يظهر “فارغة”.
- عرض تكلفة الصيانة وحالة التحميل على التأمين إن وجدت.
- حالات البلاغ:
  - مفتوح.
  - قيد التنفيذ.
  - مكتمل.
  - ملغي.

### التقارير

- توحيد شكل كل التقارير.
- تقارير داخل التطبيق يجب أن تكون واضحة ومفلترة.
- تقارير PDF يجب أن تكون رسمية:
  - جدول.
  - إجماليات.
  - شعار.
  - بيانات المكتب.
  - تاريخ الإصدار.
- عدم استخدام UI الشاشة كقالب PDF.

### صفحة المزيد

- تحويلها إلى صفحة إعدادات وخدمات منظمة:
  - التقارير.
  - الخدمات والعدادات.
  - الصيانة.
  - الرسائل.
  - النسخ الاحتياطي.
  - الإعدادات.
- إذا بقي زر “المزيد” عائماً، يجب ألا يغطي الفوتر أو المحتوى.

### الإعدادات

- تنظيمها إلى أقسام:
  - بيانات المكتب.
  - الشعار.
  - العملة.
  - PDF.
  - القفل المحلي.
  - النسخ الاحتياطي.
  - الرسائل.
- إعدادات PDF يجب أن تسمح ببيانات المكتب والشعار.

## المخاطر المحتملة

- تعديل التصميم قد يكسر وظائف موجودة إذا تم تغيير التدفقات بدون فصل واضح.
- تغيير المكونات المشتركة قد يؤثر على كل الشاشات.
- RTL قد يسبب قصاً أو محاذاة خاطئة إذا لم يختبر على شاشة صغيرة.
- PDF قد يفشل إذا تم تغيير الخطوط أو اتجاه النص بدون اختبار.
- زيادة الحركة أو الظلال قد تؤثر على الأداء.
- تغيير Bottom Navigation قد يربك المستخدم إذا اختفت وجهات مهمة.
- توحيد الألوان بدون مراجعة التباين قد ينتج نصاً ضعيفاً.
- تغيير النماذج قد يسبب فقدان بيانات مدخلة إذا لم نعالج unsaved changes.

## كيفية الحفاظ على جميع وظائف التطبيق دون تغيير

- لا يتم تغيير Repository أو قاعدة البيانات أثناء مرحلة التصميم إلا بموافقة منفصلة.
- كل شاشة يتم تعديل UI لها فقط مع إبقاء providers والعمليات كما هي.
- قبل تعديل الشاشة:
  - تحديد الوظائف الحالية.
  - تحديد الأزرار الحالية.
  - تحديد التنقلات الحالية.
  - تحديد حالات loading/error/empty.
- بعد التعديل:
  - تجربة نفس السيناريوهات.
  - مقارنة النتائج.
  - تشغيل `flutter analyze`.
  - تشغيل الاختبارات.
  - بناء APK debug عند نهاية كل مجموعة شاشات.
- أي زر PDF أو رسالة أو حفظ يجب أن يحتفظ بنفس الدالة الحالية.
- أي تغيير في النصوص يجب ألا يغير القيم المخزنة في قاعدة البيانات.
